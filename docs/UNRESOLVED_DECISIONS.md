2. **RPO — how much data loss is acceptable in a disaster?**
   **Owner decision recorded: RPO = 24h.** Current reality: automated backups run **daily** (`routes/console.php` → `clinic:backup`, `->daily()->withoutOverlapping()`), encrypted at rest (AES-256, APP_KEY-derived), retained for **30 days** (`BackupService::rotateOldBackups()`), stored under `storage/app/private/system/` (default `local` disk; configurable via `filesystems.backup_disk` / `BACKUP_DISK`); a full create→encrypt→verify→restore drill is proven green (`BackupRestoreDrillTest`, 7 tests). The 24h target holds only where `schedule:run` is invoked — the scheduler ships in `deploy/` (`deploy/cronjob.yaml` for k8s; `laravel-schedule` supervisord program for compose, runbook §6) and must be applied (kubectl/supervisorctl) plus verified on staging (checklist §4). Optional tighten (twice-daily) is a schedule-only change; consider it when data-loss tolerance shrinks.

3. **RTO — how fast must the system be restorable?**
   **Owner decision recorded: RTO = 1h.** Mechanical restore is now measured, not guessed: **~515 ms end-to-end** on a 35,000-row / 10.9 MB SQLite snapshot through the real `clinic:restore --force` (phase breakdown + copy-paste procedure in `docs/DISASTER_RECOVERY_RUNBOOK.md`), leaving the full hour budget for detection→access→decision→verify→communication. The two remaining unknowns are operational, not mechanical: **(a)** the `mysqldump`/`mysql` import path must be timed on MySQL staging (G4 — expected minutes, checklist produced); add its numbers to the runbook §6 table when measured. **(b)** Fresh-server **provisioning** (OS/PHP/composer/migrate/deploy) is not included and can exceed 1h unless the deploy pipeline is rehearsed — owners/ops should dry-run the runbook's §5 path once on staging before trusting the number.
